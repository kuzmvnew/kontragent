# ROADMAP — Kontragent

Последнее обновление: 15.09.2026

## Цель проекта

Создать сервис проверки юридических лиц и ИП в России.

Основной принцип продукта:

официальные данные
→ нормализация
→ конкретные факты и проверки
→ понятные риски
→ полезная карточка компании
→ публичный продукт
→ SEO-трафик
→ монетизация

---

# Основные правила

1. Двигаемся по фазам последовательно.
2. Не начинаем новую крупную фазу без фиксации результата предыдущей.
3. Допускается заранее строить технический фундамент следующих фаз, если это необходимо текущей фазе.
4. Не повторяем уже завершенную работу.
5. После крупных изменений обязательно запускаем тесты.
6. Актуальный код хранится в GitHub:
   kuzmvnew/kontragent
7. Текущее состояние проекта хранится в:
   PROJECT_STATUS.md
8. Этот файл является основным roadmap проекта.
9. Существенно менять порядок или содержание фаз без отдельного решения Михаила нельзя.
10. Массово открывать публичные страницы и SEO-индексацию можно только после прохождения обязательного Security & Resilience Gate между фазами 7 и 8.

# ОБЯЗАТЕЛЬНЫЙ SECURITY & RESILIENCE GATE — ПЕРЕД ФАЗОЙ 8

Статус: 🔵 ЗАПЛАНИРОВАН. БЕЗ ЕГО ПРОХОЖДЕНИЯ МАССОВЫЙ ПУБЛИЧНЫЙ SEO-РЕЛИЗ ЗАПРЕЩЁН.

## Цель

Не допустить, чтобы публичный запуск привёл к потере продукта, базы, доступности сервиса, данных, домена, секретов или неконтролируемому копированию продукта сторонними ботами.

Это не новая номерная фаза и не меняет порядок ROADMAP. Gate является обязательным критерием допуска от фазы 7 к публичной фазе 8.

## 1. DDoS, сетевые атаки и перегрузка

- поставить внешний CDN / reverse proxy / WAF с DDoS-защитой перед приложением;
- origin-сервер не должен быть доступен в обход защитного слоя без необходимости;
- настроить rate limiting на поиск, карточки, API, авторизацию и дорогие endpoints;
- ограничить соединения, таймауты запросов и максимальные размеры запросов;
- предусмотреть защиту от резкого роста нагрузки и неконтролируемых расходов инфраструктуры;
- провести нагрузочную и аварийную проверку до открытия большого числа страниц.

## 2. Anti-bot и защита от массового парсинга

- не блокировать легитимных поисковых роботов, необходимых для SEO;
- различать обычных пользователей, поисковых роботов и подозрительную автоматизацию;
- применять поведенческие лимиты по IP, сессии, аккаунту, API-ключу и классу endpoint;
- использовать challenge / CAPTCHA только для подозрительного трафика, не ухудшая обычный пользовательский сценарий;
- усиливать ограничения для datacenter/proxy/аномального трафика и массового последовательного обхода карточек;
- защищать массовый экспорт и API отдельными квотами и правами;
- логировать признаки массового выгребания базы и иметь механизм быстрой блокировки.

## 3. Web/API security

- проверка типовых рисков OWASP для web/API;
- защита от SQL injection, XSS, CSRF там, где применимо, path/header injection и небезопасных redirect;
- строгая валидация входных данных;
- secure headers и корректные cookie/security-настройки;
- зависимости с фиксированными версиями, dependency scanning и своевременными security updates;
- secret scanning репозитория;
- секреты, пароли и API-ключи не хранятся в Git.

## 4. Аккаунты, администрирование и доступы

- MFA/passkeys для GitHub, хостинга, DNS/регистратора, админ-панели и критичных сервисов;
- принцип минимально необходимых прав;
- административные интерфейсы не выставляются как обычные публичные endpoints;
- защищённый административный доступ через VPN/allowlist/эквивалентную схему при необходимости;
- аудит критичных административных действий;
- защита от credential stuffing и перебора паролей при появлении пользовательских аккаунтов.

## 5. PostgreSQL и данные

- PostgreSQL не доступен напрямую из публичного интернета;
- firewall/security groups разрешают только необходимые соединения;
- отдельные пользователи БД с минимальными правами;
- connection limits, query timeouts и защита от тяжёлых запросов;
- регулярные автоматические backup;
- point-in-time recovery или эквивалентный механизм восстановления для production;
- резервная копия хранится отдельно от production;
- backup считается рабочим только после успешного тестового восстановления.

## 6. Защита от потери или повреждения данных

- сохранять проверенную предыдущую версию данных до успешной публикации новой;
- обновления источников: download/checksum → staging → import → validate → atomic publish;
- при сбое новая версия не должна повреждать или заменять последнюю рабочую;
- иметь историю импортов и возможность установить, какая версия данных опубликована;
- использовать правило резервирования, исключающее единственную копию критичных данных на одном устройстве или одном сервере.

## 7. Безопасный deploy и защита от нашей ошибки

- production и staging разделены;
- изменения проходят тесты до production;
- критичные миграции БД имеют план отката или безопасного восстановления;
- production release идентифицируется commit/tag/version;
- должна существовать возможность быстро вернуть предыдущую рабочую версию;
- защищать основную ветку и не использовать домашний ПК как единственный источник кода.

## 8. Мониторинг и раннее обнаружение проблем

- мониторинг доступности сайта и API;
- ошибки приложения и рост 4xx/5xx;
- CPU, RAM, disk, DB connections, медленные запросы и очередь фоновых задач;
- аномальный трафик, попытки перебора и массовый scraping;
- состояние ingestion/обновлений данных;
- предупреждения о заполнении диска, истечении сертификатов и других критичных ресурсах;
- budget/cost alerts для облачной инфраструктуры;
- уведомления должны доходить до Михаила, а не существовать только в логах.

## 9. Независимость production от домашнего ПК

- домашний Windows-ПК может быть worker/dev-узлом, но не единственной точкой отказа production;
- отключение света, интернета или поломка домашнего ПК не должны останавливать публичный сервис;
- код хранится в GitHub, production и резервные копии живут независимо от домашнего ПК;
- фоновые задания должны уметь продолжить работу или догнать пропущенный цикл после восстановления worker;
- для домашнего worker предусмотреть UPS и автоматический запуск нужных сервисов после восстановления питания, если этот узел реально используется в production-процессах.

## 10. Домен, DNS и критичные внешние аккаунты

- MFA у регистратора домена и DNS-провайдера;
- registry/domain lock, если доступен;
- документировать, где находятся DNS, домен, hosting, backups и ключевые доступы;
- иметь процедуру восстановления доступа без зависимости от одного устройства;
- контролировать сроки домена, TLS-сертификатов и платных инфраструктурных сервисов.

## Критерий прохождения Gate

Перед массовым открытием страниц для индексации должны быть фактически проверены, а не только описаны:

- DDoS/WAF/CDN-защита включена;
- rate limits и anti-bot правила работают и не блокируют нормальных пользователей и нужных SEO-роботов;
- origin и PostgreSQL не открыты наружу сверх необходимого;
- секреты не находятся в Git;
- MFA включена на критичных аккаунтах;
- backup выполнен и успешно восстановлен в тестовой среде;
- проверен rollback приложения и безопасный сценарий сбоя обновления данных;
- настроены мониторинг и реальные alerts;
- проведён базовый security review приложения и зависимостей;
- проведён нагрузочный/abuse-тест основных публичных endpoints;
- существует короткая инструкция Disaster Recovery: что делать при падении сервера, повреждении БД, потере домашнего worker, компрометации ключа/аккаунта и проблеме с доменом/DNS.

Если хотя бы один критичный пункт не выполнен, публичный SEO-запуск откладывается, но разработка следующих внутренних функций может продолжаться.

# ПРАВИЛО СМЕНЫ ЧАТОВ

Не создавать новый чат после каждой маленькой задачи.

Новый чат внутри ChatGPT Project создаётся:

- после завершения крупной фазы;
- если текущий чат стал чрезмерно большим и медленным;
- если начинается крупная самостоятельная область проекта.

ChatGPT должен сам сообщать Михаилу, когда рекомендуется открыть новый чат.

При переходе в новый чат источниками истины являются:

1. ROADMAP.md
2. PROJECT_STATUS.md
3. актуальный GitHub
4. контекст ChatGPT Project

Не требуется вручную переносить всю историю старого чата.

---

# ОБЯЗАТЕЛЬНЫЙ ЦИКЛ ПОСЛЕ КРУПНОЙ ЗАДАЧИ

1. Реализовать задачу.
2. Запустить тесты.
3. Проверить результат.
4. Сделать commit.
5. Сделать push.
6. Обновить PROJECT_STATUS.md.
7. При необходимости обновить ROADMAP.md.
8. Только после этого переходить к следующей крупной задаче.
