## Реальные данные и ошибки
До большой записи в БД проверь реальную структуру официального ответа, а для bulk — весь согласованный архив, не только пример. Один работник, ограниченная нагрузка, cache reuse; не запускать миллионы запросов без плана.
Не скрывать ошибки, не пропускать запись ради зелёного теста, не считать неполную загрузку полным snapshot. Не требовать необязательное поле как обязательное вопреки официальной схеме. Если источник допускает неполные подробности, сохранить сам факт, отдельно неизвестные поля и ограничения. Пример W1-003: ИнфНаруш=1 при отсутствии подробностей остаётся положительным признаком, а не false.
Подтверждённый дефект счётчика источника нельзя молча отключить: отдельный аудит полного архива, CRC/EOF, независимые количества, SHA-256, PostgreSQL reread и видимый quality warning. Не объявлять полноту внутренней БД ведомства по одному ZIP.

## Шесть критериев для каждого источника
1. Автоматические тесты.
2. Реальная компания и настоящий официальный ответ, понятный нашему parser/provider.
3. Сохранение и независимое повторное чтение пользовательской PostgreSQL.
4. found / not_found / not_applicable / unavailable или эквивалент; ошибка и непроверенность никогда не означают всё хорошо. N/A объяснять отдельно.
5. Фактически открытая реальная карточка Chromium/Playwright: found и not_found, HTTP, видимый текст, page_errors и screenshots. Шаблон/HTTP-тест не заменяет браузер.
6. Числа, даты и измеренное exact-ID покрытие реального Master. On-demand кэш не выдавать за полную выгрузку.
Каждый критерий отдельно PASS / NOT CONFIRMED / N/A с причиной. ACCEPTED только по фактическому evidence. Код готов, данные загружены, PostgreSQL подтверждён, браузер проверен, покрытие измерено и auto_update настроен — разные статусы. NOT_CONFIGURED не превращать в настроенное расписание из-за ручного sync.
