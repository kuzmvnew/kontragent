# W1-003 — признак нарушения и отсутствие подробностей

> Исторический отчёт этапа исправления. Финальная локальная приёмка W1-003 теперь ACCEPTED: см. [W1_003_ACCEPTANCE.md](W1_003_ACCEPTANCE.md). Старые NOT ACCEPTED ниже относятся к прошлым попыткам.


Дата: 16.09.2026. Исправление ошибки локальной приёмки на `6679d97`.

## Причина остановки

В официальном сентябрьском XML встретился факт с `ИнфНаруш=1` без дочерних элементов `Нарушения`. Старый обработчик запрещал такое сочетание и останавливал импорт. Оно не означает отсутствие ИНН, повреждение архива или отсутствие нарушения.

Официальная структура: `https://file.nalog.ru/opendata/7707329152-rsmppp/structure-20230615.xsd`. Элемент `Нарушения` имеет `minOccurs=0`; доступность подробностей проверяется отдельно от самого признака. CI дополнительно читает официальную схему и проверяет это объявление.

## Семантика исправления

- `ИнфНаруш=1`: сохраняется код `1`, сервис возвращает `has_violation=True`.
- Отсутствующие подробности сохраняются пустым списком; даты, вид нарушения и его устранение не выдумываются.
- Карточка показывает предупреждение о нарушении и текст: «В выгрузке ФНС установлен признак нарушения, но подробности нарушения не предоставлены. Отсутствие подробностей не означает отсутствие нарушения».
- `ИнфНаруш=2`: сохраняется исходное отрицательное значение признака.
- Отсутствующий признак остаётся неизвестным, не превращается в `False`.
- Неизвестный код вне поддерживаемых значений продолжает блокировать обработку.

Факт поддержки не пропускается. Наличие и отсутствие факта поддержки (`found` / `not_found`) по-прежнему отделены от сведений о нарушениях. Ошибка, незагруженный или неопубликованный snapshot остаются `unavailable`.

## Счётчики качества

Успешный импорт сохраняет в `IngestionRun.details.source_quality`:

- `scope=persisted_company_ip_facts`;
- `violation_flagged_records` — количество фактов ЮЛ/ИП с кодом `1`;
- `violation_missing_details_records` — сколько из них не имеют подробностей.

Эти записи входят в общее количество сохранённых фактов, не в rejected/skipped. NPD-only физлица по-прежнему учитываются отдельно и не сохраняются в Company.

## Проверки

`tests/test_fns_sme_support_violation_details.py` проверяет сохранение признака, вложенный официальный формат, exact-INN получателя/поставщика, отрицательное и неизвестное состояние, отклонение неизвестного кода и предупреждение шаблона.

`tests/acceptance/run_w1_003_full_parser.py` предназначен исключительно для изолированного CI. Он получает один полный сентябрьский ZIP, проверяет его XML независимым счётчиком и рабочим parser, а точный проблемный документ пропускает через отдельную PostgreSQL и настоящий Chromium. Отчёт явно отделяет этот результат от пользовательской БД и её покрытия. Полный dataset не публикуется в CI-артефактах.

Проблемный файл: `VO_SVMSP_0000_9965_20260915_03ce0b33-b0a9-4670-81f4-c0fa81433098.xml`.
Идентификатор документа: `78088af2-495c-409b-8d7d-fe5c1f910517`.

## Граница полной приёмки

Исправление parser, зелёный CI и полный разбор архива сами по себе НЕ означают `W1-003 ACCEPTED`. Требуется успешный пользовательский прогон:

```bash
uv run --with playwright==1.63.0 python -u -m scripts.accept_fns_sme_support --tests --sync --browser
```

Он должен подтвердить все шесть критериев: tests, реальный официальный ответ, полный PostgreSQL write/read, состояния, реальные браузерные карточки и измеренное покрытие фактического Master Registry. Числа CI нельзя выдавать за числа пользовательской PostgreSQL.

Новая миграция не требуется: `f7b2d8a4c1e3`. Контроль полной выгрузки, CRC/EOF/SHA-256, независимые счётчики и уникальность записей не отключаются. `КолДок` с расхождением остаётся `MISMATCH`, а не `PASS`.

`auto_update=NOT_CONFIGURED`. W1-001/W1-002, архитектура и порядок roadmap не меняются.
