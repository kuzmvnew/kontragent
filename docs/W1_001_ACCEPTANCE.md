## Официальный канал и нагрузка

Официальная документация: https://www.cbr.ru/development/warning-list/
Полный JSON: https://www.cbr.ru/inside/warning-list/black-list-json
Один запрос полного списка на явный запуск. Не обходить миллионы ИНН, не скрапить HTML.
Дата `data_date` здесь — дата получения в UTC, не неподтверждённая дата состояния всего реестра. Даты внесения/обновления каждой записи считаются отдельно.

Успешная публикация заменяет только текущий W1-001 snapshot и в той же транзакции меняет его маркеры и журнал. При ошибке старые строки и дата остаются. Новые попытки скачивания записываются и при сетевой ошибке. `--force` оставлен для совместимости: каждый явный запуск валидирует полный ответ; исторический checksum не позволяет молча пропустить отсутствующую/повреждённую текущую таблицу.

`refresh_schedule=daily` — только метаданные. Реальное автоматическое расписание этой задачей НЕ включено.

## Запуск на Mac после получения проверенного кода

Из `/Users/mikhailkuznetsov/Documents/kontragent`, с существующим `.env`:

```bash
uv run --with playwright==1.63.0 python -m playwright install chromium
uv run --with playwright==1.63.0 python -m scripts.accept_cbr_warning_list --tests --sync --browser
```

Скрипт сам поднимает отдельный FastAPI на свободном loopback-порту, открывает Chromium, затем останавливает только свой сервер. Существующий dev-сервер не завершает. PostgreSQL берётся из текущего DATABASE_URL; секреты в отчёт не выводятся. Master Registry не изменяется. При миграции уже на head повторное создание таблиц не требуется.

Только отчёт по текущей БД без записи и без нового запроса источнику:

```bash
uv run python -m scripts.accept_cbr_warning_list
```

Без `--sync`, `--tests` и `--browser` соответствующие пункты не объявляются подтверждёнными. Скрипт возвращает ненулевой код при неполной приёмке.

Отчёт, tests.log и скриншоты: `data/acceptance/w1-001/<UTC timestamp>/`. Каталог data игнорируется Git. Не публиковать `.env`, полные дампы базы или сырые SQL/server logs с секретами.

## Изолированная CI-проверка

`.github/workflows/w1-001-acceptance.yml` запускает PostgreSQL 17, существующие миграции, unit tests и Chromium.
`tests/acceptance/run_w1_001.py` разрешает тестовые записи только при `GITHUB_ACTIONS=true`, loopback PostgreSQL, database `test`.

Синтетические записи используются только для детерминированных состояний и rollback. Они явно помечены SYNTHETIC и не выдаются за реальную компанию. После этого отдельно выполняется одна загрузка официального списка. Реальная 10-значная запись используется для проверки экрана на временном тестовом master; это не оценка покрытия многомиллионной базы на Mac.

Исторически часть domain-таблиц создавалась вне Alembic. Поэтому для временного CI-стенда после проверки миграций дополняются отсутствующие таблицы из существующих ORM-моделей. Это не ремонт пользовательской БД и не подтверждение полной воспроизводимости всех исторических миграций.

CI сохраняет только сводный JSON и скриншоты, не полный список/дамп. Сбой официального запроса остаётся NOT_ACCEPTED, даже если синтетические проверки прошли.
