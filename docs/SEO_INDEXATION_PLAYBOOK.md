# SEO Indexation Playbook — Next Profile MVP

Статус: planning / применять после Security & Resilience Gate перед массовой публичной индексацией.

Цель: подготовить Next Profile и первые 10 000 карточек компаний к корректному обходу, индексации, измерению поискового трафика и автоматическому обновлению семантики.

## 0. Что нужно получить от владельца проекта перед включением

Не хранить секреты в GitHub.

Нужны через env/secrets:

- `YANDEX_METRIKA_COUNTER_ID`
- `YANDEX_WORDSTAT_API_KEY`
- `YANDEX_CLOUD_FOLDER_ID` или эквивалентный идентификатор, если требует выбранный способ API
- `KEYS_SO_TOKEN`
- `PUBLIC_BASE_URL` — финальный production domain
- `INDEXNOW_KEY`

Дополнительно:

- подтвержденный аккаунт Яндекс Вебмастера;
- доступ владельца к счетчику Метрики;
- Keys.so тариф с REST API (API доступен на Professional / Corporate по текущей документации Keys.so).

## 1. Публичная URL-архитектура

Рекомендуемый стабильный формат карточки:

`/company/{slug}-{inn}`

Пример:

`/company/romashka-6671234567`

Требования:

- ИНН всегда присутствует в canonical URL;
- slug — только человекочитаемая часть;
- смена названия компании не должна ломать идентификацию;
- старый slug при изменении названия -> 301 на новый canonical;
- один ИНН -> один индексируемый canonical URL;
- GET-параметры фильтров/источников не должны создавать индексируемые дубли.

## 2. Index eligibility gate

Карточка получает `index,follow` только если:

- компания выбрана в SEO-пул;
- пройден completeness gate;
- пройдены privacy/publication restrictions;
- страница отдает HTTP 200;
- HTML содержит полезный контент без обязательного выполнения клиентского JS;
- canonical указывает на саму страницу;
- title/H1 уникальны и корректны;
- нет технических заглушек/пустых критичных блоков;
- источники и даты актуальности отображаются корректно.

Остальные публично доступные карточки до готовности:

- `noindex,follow`, либо
- не публикуются вообще — решение зависит от продукта.

Не использовать Sitemap как способ заставить индексироваться неготовые страницы.

## 3. Контент против low-value/low-demand

Яндекс может исключать страницы как малоценные/маловостребованные, если они дублируются, не содержат видимого роботу контента или плохо соответствуют реальным запросам.

Поэтому каждая индексируемая карточка должна иметь фактически полезные данные, а не просто одинаковый шаблон.

Минимум:

- точное название + ИНН/ОГРН/КПП;
- статус;
- адрес/регион;
- руководство/учредители в разрешенном объеме;
- финансовые показатели при наличии;
- проверки и факты;
- рисковые сигналы только с объяснением;
- актуальность данных;
- ссылки на официальные источники/описание источников;
- блоки, которые реально отвечают на высокоинтентные запросы конкретной компании.

SEO-тексты ради объема не генерировать.

## 4. Title / H1 / Description

Пример title:

`ООО «Ромашка» — ИНН 6671234567: реквизиты, директор, выручка, проверки | Next Profile`

Пример H1:

`ООО «Ромашка» — проверка компании по ИНН 6671234567`

Description формировать только из реально присутствующих данных и не обещать то, чего на карточке нет.

Уникальность достигается фактическими атрибутами компании, а не искусственным SEO-текстом.

## 5. robots.txt

Production robots должен:

- разрешать canonical публичные карточки;
- закрывать auth/account/admin/internal/API/debug/search-result технические страницы;
- не закрывать sitemap;
- содержать ссылку на sitemap index.

Пример каркаса:

```txt
User-agent: *
Disallow: /admin/
Disallow: /api/
Disallow: /account/
Disallow: /login
Disallow: /internal/

Sitemap: https://example.ru/sitemap-index.xml
```

Финальный файл генерируется после утверждения production routes.

## 6. Sitemap

Яндекс допускает до 50 000 URL и до 50 MB на один sitemap. Для MVP в 10 000 URL технически достаточно одного файла, но для диагностики лучше разбить, например, на 5 файлов по ~2 000 карточек.

Структура:

- `/sitemap-index.xml`
- `/sitemaps/companies-0001.xml`
- `/sitemaps/companies-0002.xml`
- ...
- `/sitemaps/static.xml`

В sitemap помещать только canonical + index-eligible URL.

`lastmod` менять только при реальном существенном изменении карточки, а не ежедневно у всех URL.

Все sitemap URL должны отдавать HTTP 200.

## 7. IndexNow

Яндекс поддерживает IndexNow.

Использовать для событий:

- новая карточка получила eligibility -> notify URL;
- карточка существенно обновлена -> notify URL;
- карточка удалена/стала недоступна -> notify URL;
- canonical изменился -> notify новый и корректно обработать старый URL.

Ключ IndexNow хранить как secret/env.

Не заменяет Sitemap: использовать вместе.

## 8. Яндекс Метрика

### Создание

1. Войти в Яндекс Метрику под рабочим Яндекс ID.
2. Создать один production-счетчик для основного домена Next Profile.
3. Включить нужные функции (например, Вебвизор) после проверки privacy/CSP.
4. Скопировать `counter_id` в secret `YANDEX_METRIKA_COUNTER_ID`.

### Установка

Код счетчика должен присутствовать на всех публичных страницах, включая SEO-карточки.

Если интерфейс SPA/клиентская навигация — корректно отправлять виртуальные pageview/hit при смене маршрута. Для JS-событий использовать `reachGoal`.

### Стартовые цели MVP

Рекомендуемые события:

- `search_submit`
- `search_result_open`
- `company_card_view` (если нужен отдельный event сверх pageview)
- `risk_section_open`
- `source_open`
- `login_start`
- `signup_start`
- `signup_complete`
- `pricing_open`
- `lead_submit`

Не передавать в Метрику ИНН/ФИО/телефоны/e-mail как персональные параметры без отдельной privacy-проверки. Для аналитики достаточно категорий/типов действий и внутренних обезличенных идентификаторов, если это допустимо политикой.

## 9. Связка Метрика <-> Яндекс Вебмастер

После подтверждения сайта в Вебмастере:

1. В Вебмастере выбрать сайт.
2. Настройки -> Привязка к Яндекс Метрике.
3. Добавить номер счетчика.
4. В Метрике подтвердить запрос привязки.
5. В Вебмастере включить обход сайта по данным счетчика.

Это дополнительный канал обнаружения посещаемых страниц роботом Яндекса.

## 10. Яндекс Вебмастер

После появления production domain:

1. Добавить сайт в Вебмастер.
2. Подтвердить права на домен/сайт.
3. Проверить robots.txt.
4. Проверить Sitemap через валидатор.
5. Добавить `sitemap-index.xml` в Индексирование -> Файлы Sitemap.
6. Связать Метрику и включить обход по счетчику.
7. Проверить несколько карточек инструментом проверки ответа сервера.
8. Для небольшого приоритетного набора можно использовать ручной «Переобход страниц», но массовые 10 000 передаются через Sitemap/счетчик/IndexNow.
9. Мониторить Индексирование -> Страницы в поиске -> Исключенные страницы, особенно `LOW_DEMAND`.

Индексация не гарантируется самим фактом отправки URL. Страница должна быть полезной и отвечать реальному спросу.

## 11. Wordstat API

На 2026 год Wordstat API доступен в Yandex Cloud / Search API и используется программно для статистики запросов.

Основные методы/задачи:

- top queries / associations;
- dynamics;
- regions distribution;
- regions tree.

Практический setup:

1. Создать/использовать Yandex Cloud.
2. Включить Yandex Search API / Wordstat функциональность.
3. Создать сервисный аккаунт по принципу минимально необходимых прав.
4. Создать API-ключ с ограниченной областью/сроком, если доступно.
5. Положить ключ только в secret/env `YANDEX_WORDSTAT_API_KEY`.
6. Реализовать rate limit, retry/backoff и кэш результатов.
7. Сохранять дату измерения и регион каждой частотности.

Публично объявленные тарифы при переходе Wordstat API в GA в мае 2026:

- GetTop: 20 RUB / 1000 запросов;
- GetDynamics: 20 RUB / 1000 запросов;
- GetRegionsDistribution: 50 RUB / 1000 запросов;
- GetRegionsTree: бесплатно.

Перед массовым запуском проверить актуальную тарификацию в Yandex Cloud.

## 12. Keys.so API

По актуальной документации Keys.so REST API:

- авторизация персональным токеном;
- токен создается в настройках ЛК в блоке API;
- передается в заголовке `X-Keyso-TOKEN`;
- API доступен на тарифах Professional и Corporate;
- текущий общий лимит документации: 10 запросов за 10 секунд;
- при HTTP 429 учитывать `Retry-After`.

Практический setup:

1. В Keys.so открыть настройки аккаунта.
2. Найти REST API.
3. Активировать REST API.
4. Сформировать токен.
5. Сохранить его в secret/env `KEYS_SO_TOKEN`.
6. Никогда не вставлять токен в GitHub, issue, чат-лог или frontend.

Для нашего SEO pipeline использовать прежде всего:

- запросы/семантику доменов конкурентов;
- запросы конкретных URL карточек;
- конкурентные URL;
- SERP;
- Wordstat/position monitoring при необходимости;
- поиск long-tail ключей.

Основные конкурентные домены для исследования задаются конфигурацией, а не хардкодятся в бизнес-логике.

## 13. Отбор и публикация: batch strategy

Не публиковать 10 000 одномоментно до проверки качества.

Рекомендуемый rollout:

- Batch 0: 50 тестовых карточек (техническая проверка);
- Batch 1: 200 карточек;
- Batch 2: 750 карточек;
- Batch 3: довести до 2 000;
- Batch 4: 5 000;
- Batch 5: 10 000.

После каждого batch смотреть:

- URL discovered;
- URL crawled;
- URL indexed;
- LOW_DEMAND;
- дубликаты/canonical проблемы;
- ошибки 4xx/5xx;
- показы;
- CTR;
- позиции;
- органические визиты;
- карточки/кластеры, которые реально получают спрос.

Если доля LOW_DEMAND резко растет, не масштабировать следующий batch до исправления причин.

## 15. Безопасность и порядок фаз

Этот playbook можно подготовить заранее, но массовая публичная индексация включается только после Security & Resilience Gate, как требует текущий ROADMAP.

До этого разрешены:

- проектирование;
- локальная разработка;
- тестовый домен с `noindex`/закрытием от роботов;
- интеграционные тесты с mock/staging;
- расчет SEO-кандидатов;
- подготовка sitemap/indexnow генераторов без production publication.
