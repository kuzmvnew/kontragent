# ERKNM SOURCE PASSPORT — Генеральная прокуратура / ФГИС ЕРКНМ

Дата проверки: 15.09.2026
Статус: источник №11 текущей Фазы 3, допустимый машинный канал подтверждён.

## Источник

- Система: ФГИС «Единый реестр контрольных (надзорных) мероприятий» (ЕРКНМ).
- Оператор: Генеральная прокуратура Российской Федерации.
- Открытая часть: https://proverki.gov.ru/
- Раздел открытых данных: https://proverki.gov.ru/portal/public-open-data

## Подтверждённый способ машинного получения

Режим: **OPEN_DATA / BULK XML**.

Актуальная инструкция по открытой части ФГИС ЕРКНМ (30.12.2025) указывает, что:

- в разделе «Реестр наборов данных» можно скачать XML с перечнем доступных наборов;
- в разделе «Наборы данных» можно выбрать год и источник ФГИС ЕРКНМ (248-ФЗ);
- месячные наборы проверок публикуются в XML;
- вместе с набором доступны паспорт набора и XSD-структура;
- набор данных скачивается как архив, содержащий XML.

Для продукта не нужен scraping поисковой веб-формы и не нужен закрытый СМЭВ-доступ.

## Условия доступа и повторного использования

Официальный регламент ФГИС ЕРКНМ указывает, что доступ к информации и наборам данных открытой части не ограничивается.

На страницах паспортов открытых данных указано, что открытые данные можно использовать повторно свободно, бесплатно и бессрочно, объединять с другой информацией и использовать для создания программ/приложений при соблюдении условий:

- использовать только в законных целях;
- не искажать данные;
- сохранять ссылку на источник.

Для нашего SaaS обязательна атрибуция Генеральной прокуратуры / ФГИС ЕРКНМ в UI/метаданных источника.

## Почему не используем закрытую интеграцию

Регламент интеграции описывает СМЭВ/закрытую часть для органов государственной власти и требует соответствующей регистрации/ЕСИА. Для нашего коммерческого SaaS это не целевой канал.

Открытые XML-наборы являются правильным каналом для bulk-ingestion публичных КНМ.

## План реализации

1. Скачать один актуальный официальный архив ЕРКНМ (248-ФЗ) и XSD.
2. Зафиксировать реальную XML-структуру через inspector до написания parser.
3. Реализовать streaming parser, чтобы не держать весь XML в памяти.
4. Модель хранит минимум:
   - учетный номер КНМ;
   - ИНН/ОГРН контролируемого лица;
   - тип/вид КНМ;
   - статус;
   - плановое/внеплановое;
   - даты начала/окончания;
   - контрольный орган;
   - вид контроля;
   - сведения о выявленных нарушениях/результате, если они есть в открытом наборе;
   - дата/версия dataset и provenance.
5. Сопоставление с Master Registry — только по устойчивому ИНН/ОГРН, без fuzzy-name linkage.
6. Coverage-аудит: количество КНМ, уникальных ИНН, совпадения с Master Registry, отсутствие идентификаторов, дубли учетных номеров.
7. Service/aggregator/UI: отдельно планируемые, завершённые и проверки с выявленными нарушениями; не трактовать сам факт проверки как негатив.
8. Tests + реальный импорт + карточка + CI.

## Семантика продукта

Сам факт наличия проверки/КНМ не означает ненадёжность компании.

В продукте важно различать:

- запланировано / проводится / завершено;
- плановое / внеплановое;
- вид контроля и орган;
- были ли выявлены нарушения;
- результат/меры, если они опубликованы.

Отсутствие записи означает только отсутствие КНМ в загруженных официальных наборах/периодах, а не «компания никогда не проверялась».
