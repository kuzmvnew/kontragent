# NPD SOURCE PASSPORT — ФНС

Дата проверки: 15.09.2026
Статус: следующий обязательный источник Фазы 3.

## Источник

Официальный публичный сервис ФНС России:

`Проверка статуса налогоплательщика налога на профессиональный доход (самозанятого)`

Web UI:

`https://npd.nalog.ru/check-status/`

API endpoint:

`POST https://statusnpd.nalog.ru/api/v1/tracker/taxpayer_status`

Официальное описание API:

`https://npd.nalog.ru/html/sites/www.npd.nalog.ru/api_statusnpd_nalog_ru.pdf`

## Контракт запроса

```json
{
  "inn": "<ИНН ФЛ или ИП>",
  "requestDate": "YYYY-MM-DD"
}
```

- `inn` — ИНН налогоплательщика.
- `requestDate` — дата, на которую проверяется статус НПД.
- Дата не может быть раньше 01.01.2019 и позже текущего дня.

## Контракт ответа

Успешный ответ содержит как минимум:

```json
{
  "status": true,
  "message": "..."
}
```

- `status=true` — на указанную дату лицо являлось плательщиком НПД.
- `status=false` — на указанную дату статус НПД не подтверждён сервисом.
- Клиент должен игнорировать новые неизвестные поля/заголовки, которые ФНС может добавить без изменения версии API.

## Ограничения API

По официальному описанию:

- REST API;
- timeout клиента должен быть не менее 60 секунд;
- лимит с одного IP — не чаще 2 запросов в минуту;
- бизнес-валидация и rate limit возвращаются HTTP 422;
- неверный формат запроса — HTTP 400;
- внутренняя ошибка — HTTP 500.

## Режим использования в продукте

Классификация: `PUBLIC_LIVE / ON_DEMAND`.

Причина:

- ФНС предоставляет официальный публичный API и web-сервис;
- сервис бесплатный и не требует регистрации;
- лимит 2 запроса/мин/IP делает его непригодным для массового обхода миллионов ИНН;
- поэтому источник используется как точечная проверка по запросу пользователя/продуктовому событию, а не как bulk ingestion.

## Хранение и публикация

Без отдельного расширенного правового решения не делаем массовое зеркало статусов НПД.

Разрешённая продуктовая модель на текущем этапе:

- хранить технический результат собственной проверки вместе с `request_date`, `checked_at`, статусом ответа и источником для аудита/кэша;
- не считать сохранённый ответ бессрочно актуальным;
- для проверки текущего статуса использовать свежий live-запрос с учётом rate limit;
- публично показывать только результат проверки и дату, без лишних персональных данных;
- не запускать SEO-карточки физических лиц из этого источника.

## Применимость

В текущем продукте компаний:

- ЮЛ: `not_applicable` — юридическое лицо не является плательщиком НПД;
- ИП: источник применим, проверяем 12-значный ИНН;
- будущий Person: источник применим к физлицу при наличии подтверждённого ИНН и соблюдении privacy/source-passport правил.

## Product contract

Стандартный check-result:

- `found` — API успешно проверен и `status=true`;
- `not_found` — API успешно проверен и `status=false`;
- `not_applicable` — сущность является ЮЛ;
- `unavailable` — сервис недоступен, rate limited, ответ невалиден или live-проверку корректно выполнить нельзя.

Отсутствие успешного ответа API нельзя превращать в `not_found`.
