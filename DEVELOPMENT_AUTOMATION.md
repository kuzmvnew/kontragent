## Рабочий процесс с этого момента

Для существенных изменений предпочитаем:

`main → отдельная branch → изменение → PR → GitHub CI → merge`

Не отправлять непроверенные крупные изменения напрямую в `main`, если задача позволяет использовать PR.

Перед крупной задачей:

1. прочитать `PROJECT_STATUS.md`;
2. прочитать `ROADMAP.md`;
3. проверить актуальный `main`;
4. убедиться, что задача не дублирует уже сделанное.

После изменения:

1. автоматические тесты должны пройти;
2. результат должен быть сохранён в GitHub;
3. для законченного продуктового блока обновляется `PROJECT_STATUS.md`;
4. фиксируется следующий конкретный шаг.

## Что подключим, когда домашний ПК станет доступен

Домашний Windows-ПК планируется использовать не как единственный источник кода, а как вычислительный worker для задач, которые неудобно выполнять на Mac или в обычном GitHub-hosted CI:

- большие импорты государственных datasets;
- длительные проверки PostgreSQL;
- staging/validation больших обновлений;
- benchmark и нагрузочные проверки;
- позже — регулярное обновление datasets и другие тяжёлые jobs.

Mac остаётся устройством управления, GitHub — источником истины.

## Важное ограничение безопасности домашнего ПК

На дату фиксации репозиторий `kuzmvnew/kontragent` имеет visibility `public`.

Поэтому нельзя просто подключить домашний ПК как unrestricted self-hosted GitHub Actions runner, который может исполнять произвольные workflow/PR-задачи. Перед подключением нужно выбрать безопасную схему, например:

- перевести репозиторий/рабочий runner-контур в private-доступ; либо
- жёстко ограничить self-hosted runner доверенными workflow/ветками и не запускать на нём код из недоверенных pull request; либо
- использовать отдельный pull-based worker, который забирает только подтверждённые commits/jobs и не предоставляет GitHub произвольное выполнение команд на ПК.

До отдельной настройки безопасности домашний ПК к GitHub Actions не подключается.

## Следующие уровни автоматизации

### Уровень 2 — GitHub development workflow

- закрепить PR-first процесс;
- добавить дополнительные автоматические проверки там, где они реально нужны;

### Уровень 3 — Home worker

- безопасный удалённый доступ с Mac;
- автоматическое получение подтверждённого кода;
- запуск тяжёлых jobs;
- сохранение логов и результатов;
- защита от отключения питания/интернета и восстановление после сбоев.

### Уровень 4 — автоматизация самого продукта

Это отдельная продуктовая задача: обнаружение новых версий официальных источников, download/checksum, staging, validate, atomic publish, rollback и статусная панель актуальности datasets.

Автоматизация разработки и автоматизация обновления данных продукта — разные процессы и не должны смешиваться.
