# PERSON CHECK — источники, критерии и режим использования

Дата первичной сверки: 15.09.2026.

Связанные документы: [ROADMAP.md](ROADMAP.md) · [ROADMAP_DETAILED.md](ROADMAP_DETAILED.md) · [PROJECT_STATUS.md](PROJECT_STATUS.md)

## Цель

Собрать модуль проверки физических лиц, который по числу полезных критериев не уступает ведущим российским сервисам, но не строится на принципе «если страница открыта, её можно бесконечно парсить и перепродавать».

Этот файл — продуктово-технический backlog и предварительная проверка режима доступа. Он не является юридическим заключением. Перед включением каждого источника в production его паспорт в Dataset Registry должен отдельно подтвердить способ получения, срок хранения, право показа и коммерческого использования.

## Классы подключения

- **A — OPEN DATA**: официальный машиночитаемый набор с условиями повторного использования. Можно строить регулярный импорт; при публикации соблюдать условия источника, в том числе атрибуцию.
- **B — PUBLIC LIVE**: сведения прямо сделаны общедоступными законом/официальным реестром, но публичность может действовать только пока событие активно или в установленный срок. Нужны частые обновления и автоматическое снятие/удаление устаревшего публичного статуса.
- **C — ON DEMAND**: официальный публичный сервис/API подходит для точечной проверки, но право массово копировать и строить собственное зеркало не подтверждено. По умолчанию запрос выполняется по действию пользователя, хранится минимум необходимого.
- **D — LICENSED**: для массового машинного доступа нужен договор, платный API/выгрузка либо отдельное разрешение.
- **E — CONSENT / PRIVATE**: проверка возможна по реквизитам документа или с согласием физлица; результат не размещается в открытой публичной карточке.
- **X — EXCLUDE**: не использовать без отдельного решения и правового основания.

## Обязательный gate для любого Person-источника

До production для каждого источника фиксируем:

1. официальный владелец и URL;
2. идентификаторы для поиска и качество сопоставления;
3. официальный способ машинного получения: файл / API / web-service / on-demand;
4. допустимость автоматизации и лимиты запросов;
5. право локального хранения и кэширования;
6. право повторной публикации;
7. допустимость коммерческого использования результата;
8. срок, пока сведения являются публичными, и правило purge/expiry;
9. какие поля запрещаем показывать публично даже если они присутствуют в источнике;
10. источник, дата проверки и версия записи;
11. основание обработки персональных данных и требования к локализации/защите;
12. процедура исправления, блокировки и удаления ошибочной/устаревшей записи.

Публичная страница государственного сервиса сама по себе не означает право сделать бессрочную коммерческую копию всей базы.

| Наследственные дела | ФНП — реестр наследственных дел | C | точечный поиск; сервис имеет лимит запросов; совпадение только ФИО считать недостаточным |

## Идентификация человека

Для негативных и чувствительных сигналов запрещено автоматически утверждать совпадение только по одинаковому ФИО.

Приоритет идентификаторов:

`ИНН / иной устойчивый официальный идентификатор → ФИО + дата рождения → ФИО + дополнительные признаки → только ФИО = возможное совпадение / ручная проверка`.

Карточка должна хранить `match_confidence` и основания сопоставления.

# PERSON ENFORCEMENT — долги, взыскания, суды, банкротство

| Проверка | Официальный источник | Режим | Продуктовая реализация |
|---|---|---:|---|
| Исполнительные производства | ФССП — Банк данных исполнительных производств | B | показывать только сведения, которые остаются общедоступными; синхронизировать снятие записей |
| Вид исполнительного производства | ФССП | B | нормализовать предмет исполнения в категории, не показывать только общий счётчик |
| Алименты | ФССП — отдельный реестр должников по алиментным обязательствам + БД ИП | B | отдельный критерий и отдельный фильтр |
| Налоговые взыскания | ФССП / документ-основание | B | отдельная категория от алиментов и прочих долгов |
| Кредиты/займы, штрафы, ЖКХ, ущерб, иное | ФССП | B | отдельные нормализованные категории при достаточном основании из источника |
| Розыск ФССП | ФССП | B/C | показывать текущий официальный статус; автоматизацию проверить в паспорте источника |
| Розыск МВД | МВД России | C | on-demand/официальный допустимый интерфейс до подтверждения массового доступа |
| Розыск ФСИН | ФСИН России | C | on-demand; массовый сбор не считать разрешённым без отдельной проверки условий |
| Арбитражные дела | КАД / официальные судебные источники | C/D | предпочтительно официальный/лицензированный машинный доступ; учитывать роль лица в деле |
| Суды общей юрисдикции | ГАС «Правосудие» / официальные сайты судов | C/D | не строить вывод только по ФИО; учитывать ограничения опубликования персональных данных |
| Банкротство физлица | ЕФРСБ / Федресурс | B/D | события, стадия, даты; для массовой интеграции использовать допустимый feed/API |
| Намерение банкротства | Федресурс | B/D | отдельное событие, не смешивать с фактом уже начатой процедуры |
| РНП / закупки | ЕИС / ФАС | C/D | связывать физлицо только при надёжном идентификаторе и подтверждённом доступе |

### Нормализация ФССП

Минимальная модель:

`исполнительное производство → предмет исполнения → нормализованная категория → сумма → статус → дата → подразделение → документ-основание → источник`.

Минимальные категории продукта:

- алименты;
- налоги и сборы;
- кредиты/займы;
- административные/иные штрафы;
- ЖКХ;
- возмещение ущерба;
- иные взыскания;
- не удалось классифицировать.

Не угадывать категорию по сумме. Если предмет исполнения не позволяет уверенно классифицировать — показывать «иное/не определено».

# PERSON COMPLIANCE — публичные реестры риска

| Проверка | Официальный источник | Режим | Продуктовая реализация |
|---|---|---:|---|
| Терроризм / экстремизм | Росфинмониторинг | B | отдельный критерий; дата версии списка и актуальный статус |
| ОМУ | Росфинмониторинг — перечень по противодействию финансированию распространения ОМУ | B | отдельный критерий, не объединять с терроризмом/экстремизмом |
| Иностранный агент | Минюст России | B/C | официальный текущий статус; режим массового скачивания/переиспользования подтвердить в паспорте |
| Утрата доверия | государственный реестр лиц, уволенных в связи с утратой доверия | B | учитывать установленный срок нахождения сведений в реестре |
| Запрет посещения спортивных мероприятий | МВД России | B | показывать только пока запрет/публикация актуальны; синхронизировать исключение |
| РПДЛ / PEP | собственный реестр из официальных сведений о должностях | C/A по первичным источникам | отдельный Person PEP Registry; хранить должность, орган, период, первоисточник и confidence |
| Международные санкционные перечни | ООН / ЕС / UK и другие официальные источники | A/C/D по конкретному списку | отдельная поздняя волна; для каждого списка отдельно проверить лицензию и коммерческое повторное использование |

### РПДЛ / PEP

Не считать «политические взгляды» или партийные предпочтения. Нас интересует только публичная должность/статус, релевантный KYC/комплаенсу.

Структура:

`person → public_role → public_body/organisation → PEP category → start_date → end_date → official_source → match_confidence`.

Родственников и окружение не добавлять по догадкам или неофициальным публикациям. Такие связи возможны только при надёжном правовом и фактическом основании.

| Нотариус | ФНП / Минюст | C | профессиональный статус; массовую выгрузку подтвердить отдельно |

Для человека используем иные реестры/статусы Банка России.

# Что исключаем из базовой публичной карточки

- утечки баз, «серые» брокеры персональных данных и купленные телефонные/адресные базы;
- поиск «вся недвижимость человека по ФИО» без отдельного законного основания;
- медицинские данные, религия, политические взгляды, интимная жизнь и иные специальные категории персональных данных;
- публичное отображение паспортных данных, СНИЛС, точного домашнего адреса и других избыточных идентификаторов;
- автоматический негативный вывод по одному совпадению ФИО;
- бессрочная история сведений, которые государственный источник обязан снять из публичного доступа после окончания установленного срока.

# Бесплатно и платно — продуктовый принцип

Можно брать деньги не за «продажу государственной базы», а за собственную услугу:

`поиск → сопоставление → агрегация → нормализация → объяснение → отчёт → мониторинг → API`.

Но платность продукта не отменяет ограничений первичного источника. Если источник разрешает только точечный запрос, платный тариф не превращает его в разрешение на массовое зеркало. Если открытые данные разрешают коммерческое использование, их можно включать и в бесплатные, и в платные продукты с соблюдением условий источника.

Рекомендуемый режим карточки:

- **Public/free**: только явно разрешённые к публичному повторному использованию факты и минимально необходимые поля;
- **Account/on-demand**: PUBLIC LIVE и ON DEMAND проверки, актуальные на момент запроса, с датой и источником;
- **Person Pro/private**: документные, согласительные и лицензируемые проверки;
- **API/export**: только те поля и источники, где отдельно разрешён соответствующий способ выдачи.

# Privacy / legal production gate для Person

До публичного запуска Person должны быть реализованы как минимум:

- паспорт каждого источника в Dataset Registry;
- основание обработки персональных данных и минимизация полей;
- хранение первично собираемых персональных данных граждан РФ в базе на территории РФ в случаях, когда это требуется законом;
- проверка необходимости уведомления Роскомнадзора и выполнение обязанностей оператора ПД;
- политика обработки ПД и публичное описание источников;
- журнал происхождения данных: источник, дата, версия;
- автоматические сроки актуальности и удаление/скрытие записей после утраты публичного статуса;
- механизм обращения физлица: уточнение, оспаривание, блокировка, исправление и удаление при наличии оснований;
- защита от массового выгребания Person-базы;
- запрет SEO-индексации персональных карточек до отдельного решения после privacy/legal review;
- отдельные правила для free UI, paid report, API и bulk export.

## Критерий готовности Person source

Источник считается готовым не когда написан парсер, а когда одновременно подтверждены:

`access → identity match → ingestion/on-demand → freshness → expiry → product display → commercial/publication mode → tests → privacy controls`.

До этого его статус в roadmap остаётся «кандидат / проверяется».
